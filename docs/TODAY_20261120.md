# TripBuddy · 오늘 함께 진행할 작업

날짜: 2026-11-20 (Asia/Seoul)
목표: 사용자가 실제 화면에서 코스를 생성하고 수정·다운로드까지 사용할 수 있는지 확인한다.
진행 방식: 한 단계씩 실행 → 사용자와 결과 확인 → 문제를 수정 → 다음 단계. 실제 요청을 여러 건 자동 실행하지 않는다.

## 오늘 범위

UI에서 실제 장소·날씨·코스를 검증한다. 이미 성공한 HTTP API 테스트와 구분한다. 공개 배포, 전국 확대, 로그인, 캐릭터 자유 조합, 검색 엔진 재설계는 오늘 필수 범위에 넣지 않는다. 확인 중 드러나는 동작 오류와 표시 문제는 고친다. 새 아트 방향·규칙 완화·추가 기능은 별도로 결정한다.

## 함께 확인할 내용

각 단계에서 사용자는 실제 화면을 보고 사용감·원하는 동작을 확인한다. 에이전트는 API/실행 기록·오류·장소 ID 변경·데이터 출처를 확인한다. 사용자가 직접 실행한 작업은 유료 요청을 다시 보내 재현하지 않고 기존 결과로 우선 진단한다. 새 생성이나 추가 테스트가 필요하면 목적을 먼저 공유한다.

검증 기록은 개인정보·키를 제외해 이 문서에 추가한다. 코스 전문과 관광공사 소개글은 git 제외 data 폴더에 유지한다. 비용은 토큰 응답이 있을 때 사용량을 기록하며 응답이 없으면 0비용으로 단정하지 않는다.

- 화면의 실제 엔진 안내·캐릭터 상태 확인은 사용자와 2단계 시작 시 진행한다.

## 사용자 확인 및 문제 처리

- 사용자가 엔진 연결과 코스 확인 완료를 알림. 지도 점검 중 부산 2일 코스에서 3곳 삭제를 보고해 다음 검증을 잠시 중단함.
- 해당 체크포인트: 원본 후보 44곳(가볼 곳 11, 식당 5, 카페 19, 실내 9), 초안 포함 3회 작성 후 관광 칸에 음식점 2곳·저녁에 카페 1곳이 남아 삭제됨.
- 수정: slot_type/cafe_meal/cafe_slot을 기존 안전 교체 대상에 포함, 모델 입력에 카페 식사·관광 칸 제한 명시, 최종 동선 정렬 후 재검증, 하루 전체 위반 안내 표시.
- 저장된 마지막 초안을 네트워크 없이 재생: 교체 전 7칸·제거 3곳 → 교체 후 10칸·제거 0곳.
- 단, 재생한 코스는 하루 직선거리 상한 초과가 두 날짜에 남음(약 23km·30km, 부산 상한 21km). 규칙을 완화하거나 정상 통과로 처리하지 않음.
- 원본 테스트 346개 및 웹앱 API 테스트 31개 통과. 추가 유료 호출 없음.
- 재현 기록을 보존한 뒤 수정 사항을 반영해 실제 OpenAI 모드 서버를 재시작함. 메모리 세션은 초기화되어 새 여행으로 확인해야 하며 기존 7칸 결과가 자동 복구된 것은 아님.
- 다음: 유형 교체 수정 적용과 새 코스 재검증, 하루 동선 문제는 별도 확인.

## 후보 이름을 ID로 반환한 문제

- 원본 대화와 새 앱의 입력 조건은 같고 검색 후보는 모두 52곳. 모델 판정 후 원본 48곳·새 앱 45곳으로 달랐음.
- 새 앱 3번째 초안이 10개 content_id 모두에 ID 대신 장소 이름을 반환하여 unknown_place로 전부 제거됨. 10곳 모두 현재 후보 안에서 이름이 유일하게 일치함.
- 작성·수정 결과와 저장된 초안 검증에서 현재 후보의 유일한 정확한 이름만 ID로 복원. 기존 ID 우선, 동명이소·후보 밖·부분 일치는 복원하지 않음. 휴무·유형·거리 검증 유지.
- 저장된 초안 오프라인 재검증: ID 10개 복원, 10칸 유지, 제거 0곳. 단, 11/22 직선 합 42km > 하루 상한 21km 위반은 남음. 실제 재조회가 아닌 저장된 정보 사용 결과임.
- 원본 349개 및 API 31개 테스트 통과. 모델·외부 API 추가 호출 없음. 원본 8501은 유지하고 새 앱 서버만 재시작.
- 다음 확인: 새 코스의 ID 복원과 하루 동선 제약. 서로 다른 실행의 코스가 동일함을 보장하는 변경은 아님.

## 하루 거리 보정

- 재작성을 소진한 새 여행에서만 적용. 기존 장소 순서 조정을 먼저 시도하고, 부족하면 변경 칸 수별 제한 탐색으로 같은 날짜의 후보 조합을 다시 고른다. 수정 턴에는 적용하지 않는다.
- 후보 ID·칸 구성·유형·중복·제외·휴무·철수·박물관 수·구간 거리·하루 총거리 검사 유지. 다른 날짜와 부가 코스·카페 추천 장소를 중복 사용하지 않는다. 새 선택 장소는 기존 재조회 절차를 거쳐 새 위반이 생기면 해당 보정을 적용하지 않는다.
- 탐색은 유한하며 전역 최적해나 해 발견을 보장하지 않는다. 적합한 완성 동선이 없으면 기존 코스와 경고 유지. 합격 기준을 낮추지 않음.
- 최신 unknown_place 사례: 저장 데이터 재생에서 10칸 유지·제거 0·위반 0. 하루 직선 합 8.33/42.29km → 6.26/20.14km. 재생 약 18ms(외부 재조회 제외).
- 이전 카페 유형 사례: 10칸 유지·제거 0, 둘째 날 16.10km. 첫째 날 23.11km > 21km 경고는 남음. 모든 사례 해결로 간주하지 않음.
- 원본 357개·API 31개 테스트 통과. 추가 모델/외부 API 호출 없음. 최신 문제 초안은 DB 체크포인트에서 읽었고 재생 결과는 git 제외 data/regressions에 보존.
- 다음 공동 확인: 새 여행을 생성한 화면에서 날짜별 코스·교체 안내·거리 경고 확인. 이후 날짜 간 장소 재배치가 필요한 잔여 사례 검토.

## 반복 확인 비용을 줄이는 일괄 검증

- `npm run verify`: 원본 엔진 pytest → API pytest → 프런트엔드 타입 검사 → 저장된 실제 사례 4건 재생. 사용자에게 매 수정마다 새 여행 생성을 요청하지 않고 작업자가 내부 검증 후 묶어서 전달한다.
- `npm run test:regression`: 녹화 사례만 재생. 네트워크·자식 프로세스 차단, 저장된 후보·초안·휴무 정보 사용. SQLite는 캡처 시 읽기 전용이며 재생 시 접근하지 않음. 원본 정제 데이터도 캡처 때 휴무 필드만 고정하고 재생 시 다시 읽지 않음.
- 체크섬으로 사례 입력 고정. 누락·변조·실행 오류·새 위반·삭제·빈 칸·요청 밖 장소/이유 변경은 실패 감지. 기존 미해결 문제는 정확한 날짜/칸/ID로 지정하며 자동으로 허용하지 않는다.
- 결과: 엔진 테스트 367개·API 테스트 31개·타입 검사 통과. 실제 저장 사례 PASS 2건, KNOWN_ISSUE 2건, 새 FAIL 0건.
- 정상: 부산 이름/ID 오류 사례 10칸·위반 0, 강릉 생성 10칸·위반 0.
- 미해결: 부산 카페 사례의 11/21 하루 거리 23.11km > 21km; 강릉 점심 수정 기록의 11/22 저녁 장소는 같지만 이유 문장이 조금 바뀜. 후자는 이전 ID 비교만으로 놓쳤던 차이로 새 검증에서 발견. 두 문제를 정상 통과로 기록하지 않음.
- `--strict-known`은 이 2건도 실패 코드 1로 처리하며 실제 실행 확인. 기본 모드 코드 0은 새 회귀 없음이라는 의미이며 전체 품질 합격이 아님.
- JSON/Markdown 보고서: data/regressions/reports/latest.json, latest.md. 데이터와 녹화는 git 제외. 코드와 기대 조건만 저장소에 관리하고 TourAPI 내용을 공개하지 않음.
- 추가 모델·외부 API 호출 없음, 서버 재시작 없음. 이번 검증은 기존 초안 처리만 확인하며 최신 검색/모델 출력·최신 휴무·UI는 해당 변경 시 별도 제한 검증.
- 이후에는 남은 두 문제도 저장 사례로 수정·확인하며, 실제 호출은 모델 입력·연결 등의 변경을 검증해야 할 때 묶어서 수행한다.

## 잔여 문제 순차 처리

1. 부산 거리: 기존 후보의 가볼 곳 20곳·식당 5곳으로 가능한 136,800개 순서 배치를 전수 확인. 휴무·제외·박물관 제약을 느슨하게 하고 부가 코스 장소도 본 코스에 허용해도, 21km 이하인 장소 집합은 9개뿐이며 서로 중복 없는 이틀 조합은 0개. 따라서 현재 후보만 재배치하는 방식으로는 해결 불가능. 제한 탐색 실패가 아니라 후보 구성 부족임을 확인. 기준 완화 없이 가까운 식당 후보를 추가 검색·기존 조건 판정하는 방향을 사용자에게 제시함. 답변 전 후보 보충·실제 호출은 진행하지 않음. 실험한 공동 배치 프로토타입은 저장소에 반영하지 않음.
2. 수정 이유: 같은 날짜·칸·장소면 기존 reason 원문 유지. 추천 이유 자체의 재작성은 Route의 rewrite_reasons 명시 판정으로 허용하고 다음 턴에는 초기화. 저장된 수정 응답에도 같은 후처리를 재생하여 기존 사례 해결 확인. 녹화·기대 조건·체크섬을 변경하지 않음.
3. 일괄 검증: 엔진 369개·API 31개·타입 검사 통과. 회귀 PASS 3, KNOWN_ISSUE 1, FAIL 0. 남은 항목은 부산 후보 부족으로 인한 하루 거리 초과. 모델·외부 API 추가 호출 없음.
4. 문장 보존 수정은 새 앱 서버에 반영하며 원본 8501 서버는 유지. 새 앱 메모리 세션은 초기화됨. 실제 생성 확인은 후보 보충 방향 결정 후 제한적으로 수행할 예정.

## 지역·이동 수단별 기준안 오프라인 비교

- 사용자 요청에 따라 제안 수치를 비교용 config.PROPOSED_DAY_KM/PROPOSED_WALK_DAY_KM에 추가. 실제 MAX_DAY_KM_BY_REGION 및 MAX_LEG_KM_BY_REGION은 유지. 서버 재시작·후보 보충·유료 호출 없음.
- `npm run compare:distance`로 저장 초안과 기존 보정 결과를 각각 대중교통·자동차·도보 시나리오로 판정. 이동 수단은 사용자 입력으로 저장하거나 캐릭터에서 추정하지 않음. 입력 체크섬·원본 사례 불변.
